## 1. O que faltava

Dava para **criar** locais de estoque, mas não havia onde **ver todos**, **corrigir** um nome ou obra errados, nem **desativar** um local que não é mais usado, como o container de uma obra que terminou.

## 2. A tela nova: Estoque → Locais de estoque

Caminho: menu **Estoque** → botão **Locais de estoque**. Também dá para chegar pelo link **Gerenciar locais**, que aparece no seletor de local das telas de entrega (EPI-325).

A tabela mostra cada local com:

| Coluna | De onde vem |
|---|---|
| Local, Código | cadastro do local |
| Obra | obra ligada ao local ("Central" se não tiver) |
| Responsável | funcionário responsável |
| **EPIs em estoque** | soma do saldo de todos os EPIs naquele local |
| Situação | Ativo / Inativo |

Ações (só para **Administrador** e **Almoxarife**, os perfis que o banco deixa alterar locais):

- **Editar:** abre o mesmo formulário do "novo local", já preenchido.
- **Inativar / Reativar.**

Os inativos ficam escondidos. A caixa **"Mostrar inativos (N)"** traz eles de volta à tabela.

## 3. Por que "inativar" e não "excluir"

Um local que já teve movimentação faz parte do **histórico**: as entradas, entregas e transferências apontam para ele. Desde a **correção 10**, o banco **não deixa apagar** um local com histórico, justamente para não perder esse registro, que a NR-6 exige.

Por isso o caminho certo é **inativar**: o local some das telas de operação, mas o histórico continua completo e o local pode ser **reativado** se precisar.

## 4. Duas regras novas no banco (`13_locais_inativos.sql`)

### Regra A: não inativar local que ainda tem EPI

Se um local com 7 capacetes fosse inativado, esses 7 capacetes **sumiriam** das telas, que só mostram locais ativos, e ninguém conseguiria mais entregá-los nem transferi-los.

Para impedir isso criei um **gatilho** (trigger). Gatilho é uma função que o banco roda **sozinho** toda vez que acontece algo numa tabela. Este roda **antes de mudar o status** de um local. Se o novo status é "inativo" e a soma do saldo é maior que zero, ele recusa com a mensagem:

> *"Este local ainda tem 7 EPI(s) em estoque. Transfira o saldo para outro local antes de inativar."*

A tela já deixa o botão **Inativar** desligado nesses casos e explica o motivo ao passar o mouse. Mas a regra **também** está no banco, porque a tela pode ser contornada chamando a API direto, e porque o formulário de edição também tem o campo "Status".

### Regra B: local inativo não recebe nem entrega EPI

As telas de entrega, entrada e transferência já escondem os locais inativos. No banco, a conferência criada na **EPI-272** (`interno.exigir_local_da_empresa`) agora exige também `status = 'ativo'`. Assim, nenhuma das 4 funções (entrada, transferência, entrega, troca/devolução) aceita um local inativo, nem chamada direto pela API.

## 5. Formulário de edição

Em vez de criar uma tela nova, o `NovoLocalEstoque.jsx` passou a funcionar nos **dois modos**:

| Endereço | Modo | O que faz ao salvar |
|---|---|---|
| `/estoque/locais/novo` | criar | `insert` (com a empresa do usuário) |
| `/estoque/locais/:id/editar` | editar | carrega o local e faz `update` |

O `:id` no endereço é lido com `useParams()`, uma ferramenta do React Router que pega pedaços do endereço. Se ele existe, a tela está editando. Reaproveitar a mesma tela garante que criar e editar tenham **os mesmos campos e as mesmas validações**.

O RLS continua valendo: só Administrador e Almoxarife conseguem gravar, e só nos locais da própria empresa.

## 8. O que aprender com esta tarefa

- **Excluir x inativar:** dado com histórico não se apaga, se desativa. É o mesmo princípio da correção 10.
- **Regra importante vai no banco**, mesmo quando a tela já trata. A tela é conforto; o banco é a garantia.
- **Gatilho (trigger)** é a ferramenta para regras do tipo "antes de mudar X, confira Y".
- **Reaproveite telas** quando criar e editar têm os mesmos campos. Menos código e menos chance de os dois ficarem diferentes.
