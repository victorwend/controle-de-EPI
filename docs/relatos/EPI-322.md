## 1. O que foi pedido

1. O campo **CNPJ** deve aceitar só a quantidade certa de caracteres e ir colocando `.`, `/` e `-` sozinho, conforme a pessoa digita.
2. Criar uma regra de **senha forte**, com letras, números e caracteres.

## 2. Como estava antes

- **CNPJ:** era um campo de texto livre. Dava para digitar letras, símbolos e quantos caracteres quisesse. A tela só conferia se havia 14 números, sem ver se o CNPJ era verdadeiro.
- **Senha:** bastavam **6 caracteres quaisquer**. `123456` era aceita.

## 3. O que mudou

### 3.1 Um lugar só para as validações: `lib/validacoes.js`

Criei um arquivo só com **funções puras**, ou seja, funções que recebem um valor e devolvem um resultado, sem mexer em tela, banco ou internet. Essa separação traz três vantagens:

- dá para **testar** sem abrir o navegador (seção 5);
- dá para **reaproveitar** em outras telas, como o futuro cadastro de fornecedores;
- a tela fica mais simples, porque só chama `formatarCnpj(...)` ou `senhaForte(...)`.

| Função | O que faz |
|---|---|
| `formatarCnpj(texto)` | Devolve o texto com a máscara `XX.XXX.XXX/XXXX-XX`, cortado em 14 caracteres |
| `limparCnpj(texto)` | Tira a máscara: `11.222.333/0001-81` vira `11222333000181` |
| `cnpjValido(texto)` | Confere tamanho, formato e **dígitos verificadores** |
| `avaliarSenha(senha)` | Diz, regra por regra, o que já foi cumprido |
| `senhaForte(senha)` | `true` só se todas as regras foram cumpridas |

### 3.2 CNPJ: máscara enquanto digita

No `Cadastro.jsx`, o campo passou a fazer `setCnpj(formatarCnpj(event.target.value))`. A cada tecla:

1. tudo que não é letra nem número é jogado fora (inclusive a pontuação antiga);
2. o texto é cortado em 14 caracteres;
3. a pontuação é colocada de novo nas posições certas.

Por isso, digitar `11222333000181` ou colar `11.222.333/0001-81` dá o mesmo resultado. O campo também ganhou `maxLength={18}`, que é o tamanho com a máscara.

### 3.3 Atenção: o CNPJ agora também pode ter letras

O pedido foi "só números", mas **desde julho de 2026 a Receita Federal emite CNPJ com letras e números** (CNPJ alfanumérico, Instrução Normativa RFB nº 2.229/2024):

- as **12 primeiras posições** podem ter letras maiúsculas (A–Z) ou números;
- as **2 últimas** (dígitos verificadores) continuam sendo **só números**;
- os CNPJs antigos, só com números, continuam valendo.

Se o campo aceitasse só números, uma empresa aberta depois de julho/2026 **não conseguiria se cadastrar**. Por isso a máscara aceita letras nas 12 primeiras posições, sempre em maiúscula, e descarta letras nas 2 últimas. Para quem tem CNPJ antigo, nada muda: a pessoa digita só números.

Se a Pavidez quiser mesmo só números, basta trocar uma linha no `validacoes.js`, mas eu **não recomendo**.

### 3.4 CNPJ: dígito verificador (o "CNPJ verdadeiro")

Os 2 últimos números do CNPJ são calculados a partir dos 12 primeiros. Isso permite descobrir se alguém **digitou errado**, sem consultar a Receita. O cálculo, passo a passo:

1. cada caractere vira um número: o **código ASCII menos 48**. Para `0`–`9` dá o próprio número; para letras, `A` = 17, `B` = 18 … `Z` = 42;
2. multiplica-se cada um por um peso (2, 3, 4 … 9, voltando a 2), da direita para a esquerda, e soma-se tudo;
3. pega-se o resto da divisão por 11. Se o resto for 0 ou 1, o dígito é **0**; senão, é **11 − resto**;
4. repete-se o cálculo com o primeiro dígito incluído, para achar o segundo.

Esse é o mesmo cálculo de sempre. A única novidade é o passo 1 para as letras, que não muda nada para os CNPJs antigos.

Também recusei sequências repetidas, como `00.000.000/0000-00` e `11.111.111/1111-11`: elas passam na conta, mas não são CNPJs reais.

**Importante:** isso prova que o CNPJ foi **digitado certo**, não que a empresa **existe** ou está ativa. Para isso seria preciso consultar a Receita, o que fica fora desta tarefa.

### 3.5 Senha forte

Regras (em `REGRAS_SENHA`):

| Regra | Exemplo que falha |
|---|---|
| Pelo menos **8 caracteres** | `Ep@2026` (7) |
| Uma letra **minúscula** | `EPI@2026` |
| Uma letra **maiúscula** | `epi@2026` |
| Um **número** | `Epi@abcd` |
| Um **caractere especial** (`! @ # $ %` …) | `Epi12026` |

Exemplo que passa: `Epi@2026`.

Embaixo do campo de senha aparece a lista das regras (`SenhaRequisitos.jsx`). Cada uma **fica verde com ✓** quando é cumprida, enquanto a pessoa digita. Isso é melhor que só dar erro no final, porque a pessoa vê na hora o que falta.

A regra vale nas duas telas onde se cria senha:

- **Cadastro da empresa:** a senha do primeiro administrador.
- **Definir senha:** a tela aberta pelo link do convite e da recuperação de senha.

A tela de **login** não mudou de propósito: quem já tem senha antiga continua entrando normalmente.

### 3.6 Detalhe de acessibilidade

A lista de regras ficou **fora** do `<label>` do campo, dentro de um `<div>`. Pelas regras do HTML, um `<label>` não pode conter uma lista. A lista também tem `aria-live="polite"` e um texto escondido "(cumprido)"/"(falta)", para leitores de tela anunciarem a mudança, já que a cor sozinha não basta.

## 4. Por que também mexer no Supabase (falta fazer)

A validação na tela **pode ser contornada**: alguém pode criar a conta chamando a API do Supabase direto, sem passar pela tela. Por isso a **mesma regra precisa ser ligada no Supabase Auth**, que é quem de fato guarda a senha.

No painel do Supabase: **Authentication** → configurações de **senha** do provedor **Email** (aparece como *Password requirements* / *Minimum password length*).

- **Tamanho mínimo:** 8
- **Requisitos:** escolha a opção com **letras minúsculas, maiúsculas, números e símbolos**

O nome exato do menu pode variar um pouco conforme a versão do painel.

Com isso, mesmo quem tentar pular a tela recebe erro do próprio Supabase.

O **CNPJ** ainda não tem essa proteção no banco: a função `criar_empresa_com_administrador` aceita qualquer texto. Fica como sugestão de tarefa futura (validar o CNPJ também em SQL).

## 5. Como foi testado

**Testes automáticos** (`frontend/src/lib/validacoes.test.js`): 12 testes, todos passando. Para rodar:

```
cd frontend
npm test
```

Eles usam o executor de testes que **já vem no Node** (`node --test`), então **nenhum pacote novo** foi instalado. O que eles cobrem:

- máscara enquanto digita, limite de 14 caracteres, colar já pontuado, ignorar espaços;
- letras só nas 12 primeiras posições;
- CNPJs reais válidos (`11.222.333/0001-81`, `33.000.167/0001-01`) e o exemplo alfanumérico da Receita (`12.ABC.345/01DE-35`);
- recusa de dígito errado, tamanho errado e sequências repetidas;
- cada uma das 5 regras de senha.

**Sintaxe das telas:** conferi que os arquivos `.jsx` não têm erro de escrita. O `npm run build` não rodou aqui, porque este ambiente não acessa o servidor do npm. Ele roda no seu PC antes do PR.

## 6. Como testar na tela

1. `npm run dev` e abrir `http://localhost:5173/cadastro`.
2. **CNPJ:** digitar `11222333000181`. Deve aparecer `11.222.333/0001-81` e parar de aceitar caracteres.
3. Trocar o último número para `2` e tentar criar a conta. Deve aparecer "CNPJ inválido".
4. **Senha:** digitar devagar `Epi@2026` e ver os itens ficando verdes um por um.
5. Tentar criar a conta com `123456`. Deve ser recusada.
6. Abrir um link de convite (como o de hoje) e conferir a mesma lista na tela **Definir senha**.

## 7. O que aprender com esta tarefa

- **Separar regra de tela:** as regras ficam em funções puras, e a tela só as usa. Assim fica fácil testar e reaproveitar.
- **Validação na tela é conforto, não segurança.** A segurança de verdade fica no servidor (Supabase Auth, RLS, funções SQL).
- **Regras mudam:** o CNPJ alfanumérico é um bom exemplo. Antes de travar um formato, vale conferir se a regra oficial continua a mesma.
- **Mostrar o que falta enquanto a pessoa digita** é melhor que um erro só no final.
